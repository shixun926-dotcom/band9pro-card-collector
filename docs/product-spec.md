# 产品设计

## 1. 产品目标

在 336 x 480 的手环屏幕上提供轻量的每日集卡体验。用户每天最多通过两个
行为获得抽卡机会：

- 当天首次打开应用。
- 当天运动量达到配置目标，默认为 8000 步。

每条机会每天最多生成一次，不跨天累积。机会被抽卡消费后，当天不能再次获得。

## 2. 页面结构

### 首页

- 顶部显示当前收藏进度。
- 显示登录机会和运动机会的可用状态。
- 运动未达标时显示当前值与目标值。
- 点击可用机会进入单抽结果页。
- 底部进入图鉴。

### 图鉴

- 3 列卡册布局，适配 336 px 宽度。
- 未获得卡片显示锁定剪影和“未获得”。
- 重复卡显示持有数量。
- 点击已获得卡片进入详情。

### 详情

- 展示卡面、名称、稀有度、描述和持有数量。
- 不提供出售或分解功能，避免首版引入经济系统。

## 3. 稀有度与概率

每次抽卡先按下列总权重决定稀有度，再在该稀有度卡池中等概率抽取一张卡片。

| 等级 | 名称 | 总概率 | 卡片数量 |
| --- | --- | ---: | ---: |
| N | 普通 | 60% | 12 |
| R | 稀有 | 30% | 7 |
| SR | 史诗 | 9% | 4 |
| SSR | 传说 | 1% | 1 |

因此单张卡的实际概率为：

| 等级 | 单张概率 |
| --- | ---: |
| N | 5% |
| R | 约 4.2857% |
| SR | 2.25% |
| SSR | 1% |

首版不做保底。若需要降低长期负反馈，可在服务端增加“连续 60 抽未出 SSR
时下一抽必出 SSR”的规则，但服务端返回的卡片必须继续满足单张稀有卡概率
更低的设计目标。

## 4. 重复卡

- 重复卡直接累计数量。
- 图鉴只统计是否获得，不影响收集进度百分比。
- 首版不设置碎片、合成和交易，避免增加资源、联网和数值设计成本。

## 5. 本地规则与数据边界

首版明确采用纯本地模式，不接入服务端：

1. 客户端使用本地日期生成登录机会。
2. 运动达标后由本地状态生成运动机会。
3. 抽卡随机数和卡片归属在客户端执行。
4. 状态保存在手环本地存储中。

用户可以修改系统时间、重装应用、修改本地存储或直接修改代码。项目不盈利，
也不建立排行榜、交易或付费系统，因此不对上述行为做防护。若以后需要联网、
付费或排行，再引入服务端时间和一次性抽卡凭证。

## 6. 运动量策略

默认目标为 8000 步。若官方 SDK 不提供直接读取步数的能力，可按以下优先级
接入：

1. 穿戴健康数据接口。
2. 手机端小米运动健康数据桥接。
3. 带签名的服务端同步数据。
4. 保留手动记录入口。

由于首版接受本地数据可被修改，不再要求进行服务端签名校验。

## 7. 首版范围

包含：

- 每日登录机会。
- 每日运动机会。
- 单抽、结果展示、图鉴、详情。
- 本地展示状态与服务端接口占位。

暂不包含：

- 十连抽。
- 保底和概率公示页。
- 卡片升级。
- 碎片合成。
- 好友、排行、交易。
- 音效和复杂粒子动画。
